01

The concept

The problem, in one shopper

A shopper at an Egyptian online grocer typed حليبن — the Arabic word for milk, with one letter too many. Search returned tea sachets, chicken cordon bleu, and a beef burger. The shop stocks 322 milk products. None of them came back.

The shopper left. Nobody at the company knew it happened. That is the problem this project solves: a shop cannot fix search failures it cannot see.

What the system does

Three things, and they build on each other.

Surfaces the failures dashboard

Every query scored and ranked by impact — severity weighted by share of traffic — each with a plain-language diagnosis. Not a wall of numbers someone still has to interpret.

Zero-result and low-engagement queries each get their own sortable column and filter, so either failure class can be isolated directly. When the zero-result filter comes back empty the table says why — on this engine that is a finding, not an absence.

Proposes the fix discovery

Synonyms and misspellings mined from the log and the bilingual catalogue, each carrying the evidence that produced it, queued for a person to approve or reject. Nothing reaches live search on its own.

Answers questions agent

A natural-language agent bound to eight analytics tools, plus a weekly digest of what moved and what needs attention. Every answer reports the exact tools it called.

The design principle that shaped everything

Discovery is automated; adoption is not. A wrong synonym rule degrades search for every shopper, not one. So the system proposes with a confidence score and its evidence, and a human decides. Approving only adds a rule to an export file — deploying that file stays a separate, deliberate act.

The dataset I was given

One file: spinneys_database.sql — 828 MB, a full mysqldump of the production database behind an Egyptian online grocery. It holds 30 tables. Seven of them carry search-quality signal; the other 23 — embeddings, stock levels, price history, Django internals — are roughly 98% of the bytes and none of the signal.

The shape of the search log

This is the most important table in the project. Its real definition from the dump:

CREATE TABLE `recommendations_searches` (
  `id`          bigint       NOT NULL AUTO_INCREMENT,
  `query`       varchar(255) NOT NULL,   -- what the shopper typed
  `ar_results`  longtext     NOT NULL,   -- product titles, newline-separated
  `en_results`  longtext     NOT NULL,
  `num_results` int unsigned NOT NULL,
  `created_at`  datetime(6)  NOT NULL
)

Note what is not there: the results are stored as text, not as product foreign keys. The log says "returned the product called X", not "returned product #123". Every downstream analysis has to work from titles.

Three findings that shaped the whole design

1 — Zero-result rate is blind on this data

Not one of the 66 searches returned nothing. The engine is embedding-based and always hands back its five nearest neighbours, so failure appears as wrong results, never empty ones. A dashboard built around zero-result rate would have scored this log a perfect 100 while it was full of failures.

2 — There is no engagement data at all

No clicks, no add-to-cart, no orders. The brief asks for low-engagement queries, and they cannot be computed directly from this source. My answer was to measure what the shopper did next, and to say so everywhere the figure is reported rather than quietly presenting a proxy as the real thing.

3 — One word wearing six masks

فراولة, فاراولة, فاراولت, فراولت, فراوله, فراول — six rows in a query report, one word in the shop. Ranked as separate queries, none looks urgent. Rolled up to the term, it is the single largest source of failed searches in the log.

What the data cannot support

All 66 searches fall on 2025-01-09 within 4.5 hours, and 7.6% of them look automated. This is a QA session, not representative traffic. The rates are computed honestly but rest on a small sample — which is why I also built a mock-data generator, so the system can be exercised on 28 days of traffic with known patterns.

My workflow: 828 MB to an analytics store

The pipeline I built

  • SQL dump828 MB
    →
  • dump_readerstreaming parse
    →
  • loadernormalise + segment
    →
  • SQLiteanalytics store
    →
  • analyticsscore quality
    →
  • discovery / agentpropose + answer

One pass over the file builds every table. A full rebuild takes about 30 seconds.

Decision: read the dump directly, don't import it

  • No server to install — and no 828 MB import to sit through.
  • No credentials to handle — the file is read as text.
  • Flat memory — statements are streamed, never loaded whole.
  • A live-MySQL path exists alongside it (--source mysql) for deployments that already run the server.

On "chunking" — the terminology matters here

This is not a RAG system. There is no text chunking, no embedding computation, and no vector store. What the project does have is four genuine segmentation strategies, each solving a different problem, described below under their real names.

Worth noting: the grocer's own search engine is embedding-based — its table (recommendations_productembedding) sits right there in the dump. I skipped it deliberately, because I am measuring that engine's output, not rebuilding it.

The four segmentation strategies

Statement-level streaming I/O

The file is read line by line, with the parser tracking quote state so it knows where a statement actually ends — mysqldump can write one across several lines. Tables outside the whitelist are skipped without being parsed at all.

Rows are then buffered into batches of 5,000 before hitting the database.

ingest/dump_reader.py

Text tokenisation NLP

Every product name is normalised, then split into tokens (anything under two characters is dropped). Each Arabic token also generates variants with its prefixes stripped (ال، بال، وال، لل…) so الفاكهة and فاكهة are one term.

Result: 28,305 catalogue terms, each with the number of products using it.

text/normalize.py

Sessionisation temporal

The source records no session or user id, so sessions are derived from timing: a gap longer than 1,800 seconds starts a new one.

This is what makes "searched, then reworded" readable at all — without it there is no satisfaction signal. The 66 searches resolve into 3 sessions.

ingest/loader.py

Term rollup aggregation

Every spelling of a word folds onto one row. This is not a display convenience — it is what turns six low-priority rows into one high-priority problem.

Each term gets a verdict: spelling, retrieval gap, assortment gap, partial query, or relevance.

analytics/terms.py

Arabic normalisation, in order

The most important function in the project: every comparison between shopper text and catalogue text passes through it. The same function runs on product names at load time and on queries at query time, so the comparison is always fair.

  1. Unicode NFKC normalisation
  2. Strip diacritics (harakat, sukun, shadda)
  3. Remove tatweel (ـ)
  4. Fold letters: آ أ إ ٱ → ا · ى → ي · ة → ه · ؤ → و · ئ → ي
  5. Fold Arabic-Indic digits to ASCII
  6. Case-fold Latin text
  7. Punctuation to spaces, collapse whitespace

The judgement behind it

Normalisation must collapse the differences that carry no meaning and preserve the ones that do. فراولة and فراوله become one term — correct. But حليب and حليبن stay distinct — which is what keeps the misspelling measurable instead of silently absorbed.

Integrity, not assumption

The bulk load runs with foreign keys disabled for speed, then deletes orphaned rows (a product referenced by a category link but missing from the product table), then actually verifies that no violation remains. If one does, the load fails rather than publishing an inconsistent store.

The techniques I applied

Edit distance Damerau-Levenshtein

For misspelling detection, with a budget proportional to word length: 3 characters or fewer → zero edits, up to 6 → one edit, longer → two.

Why: two edits turn pas into pcs, an unrelated word — but the same two edits merely nudge a long word to its correct spelling.

Bilingual lexicon induction Dice coefficient

Every product carries an Arabic and an English name. Mining co-occurrence across 25,881 products induces a translation lexicon with no dictionary: حليب ↔ milk on 293 products.

Two terms that translate to the same English word are synonyms of each other — which is how لبن ≡ حليب is established by evidence rather than assumed.

Composite severity 5 signals

Each query scores 0–1 from five independent signals, weighted: lexical miss 0.30 · dissatisfaction 0.25 · incoherence 0.20 · under-fill 0.15 · instability 0.10.

The careful part: if a signal could not be measured for a given query it is dropped and the remaining weights are renormalised — so a query with no coherence reading is never silently credited with perfect coherence.

Tool-constrained agent tool use

The agent is bound to eight tools and answers only through them. It never writes SQL and never sees the database, so it cannot invent a metric — the worst it can do is pick the wrong tool, which the trace shows.

It works with no API key: a deterministic planner routes the question by intent and reads the same tools. Plainer wording, identical numbers.

Behavioural proxies, since engagement is absent

  • Followed by a repeat or rewording within 300 seconds → the result set did not satisfy.
  • Nothing followed → ambiguous, and deliberately not counted. A session ending might mean the shopper found it and checked out, or gave up. The log cannot tell those apart.
  • Re-fired within 2 seconds with identical results → not a human reaction. Flagged as automated and excluded from engagement, not deleted — which queries attract bot traffic is itself worth knowing.

The commands

searchiq etl              # build the store from the dump (~30s)
searchiq sample-data      # or: generate mock data if no dump
searchiq report           # search-quality summary in the terminal
searchiq discover         # find synonyms and misspellings
searchiq suggestions      # read the review queue
searchiq approve 3        # record a decision
searchiq export -o rules.json
searchiq ask "which queries are wasting the most traffic?" --trace
searchiq digest --days 7
searchiq export-bi        # flat tables for Power BI
searchiq serve            # dashboard on 127.0.0.1:8000

The three worst cases

حليبن — 3 searches · severity 0.59

The shopper typed "milk" with one letter too many. Search returned tea with milk, cordon bleu, and a beef burger. The catalogue holds 322 products using حليب — none came back. This is not an assortment problem, it is a retrieval fault.

فاراولت — 2 searches · severity 0.84

A misspelling of "strawberry". It returned exactly one product: Agnesi Farfalle Pasta — pasta, not strawberry, but lexically close. The catalogue holds 308 strawberry products.

فاكهة — 11 searches · severity 0.40

A perfectly spelled word meaning "fruit". Search returned a kitchen knife, a serving platter, a guava, and a bag of sugar. All 11 searches were flagged, and 100% of them were followed by another search. Not spelling — relevance.

Misspelling vs. partial query — a distinction that matters

past → pasta is not a misspelling — it is a shopper who had not finished typing. Correcting their query would change their intent. The rule I used: if the weaker term is a prefix of the stronger one, it is a partial query and the fix is autocomplete. If the weaker term is longer, the shopper typed a character too many and the fix is a spelling dictionary.

Correction direction comes from the catalogue, never from frequency

حليب is correct because 322 products use it — regardless of which spelling was typed more often. Had I ranked by frequency, a small sample with a repeated typo could flip the direction and make the system "correct" the right spelling into the wrong one.
